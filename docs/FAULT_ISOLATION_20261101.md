# 장애 주입의 소유 세션 격리 — 2026-11-01

## 재현과 영향

`FaultState.active`는 `sessionId == null`인 저장 상태를 모든 요청에 적용했다. Redis에 소유자 필드가 없는 활성 상태가 있으면 실험과 무관한 상품 조회의 캐시·DB 경로와 워커 지연에 영향을 줄 수 있었다. 정상 컨트롤 플레인이 이런 상태를 생성한다는 뜻은 아니며, 소비자가 손상되거나 불완전한 상태를 읽는 경계의 결함이다.

또한 Redis 문자열 `null`은 Jackson에서 예외가 아니라 Java null로 변환된다. 기존 `FaultStore.current()`가 null을 반환하면 소비자가 `active()`를 호출할 때 실패했다.

수정 전 회귀 테스트에서 소유자 누락, 시나리오 누락, JSON null의 3개 사례가 실패하는 것을 확인했다.

## 변경과 판단

- 장애 활성화는 비어 있지 않은 소유 세션과 현재 요청 세션의 일치를 반드시 요구한다.
- 확인할 시나리오가 null인 경우에는 활성화하지 않는다. 만료·enabled·시나리오 일치 조건도 함께 적용한다.
- JSON null은 읽기 실패 계수를 증가시키고 비활성 상태로 돌려준다. Redis 장애나 해석 실패와 동일하게 장애 주입을 끈다.
- 상품 조회 소비자 테스트로 소유자 없는 DB 장애가 느린 쿼리를 선택하지 않고, 소유자 없는 캐시 장애가 정상 캐시를 우회하지 않음을 확인한다.

장애 주입을 끄는 것은 주문이나 업무 오류를 성공 처리한다는 의미가 아니다. 추가 인증, 분산 락 또는 새 저장 구조를 도입할 필요 없이 기존 소유권 계약을 소비 지점에서 지킨다.

## 실행한 검증

Linux/WSL, Java 21.0.12.1, 저장소 Gradle Wrapper 8.14.3에서 실행했다.

```bash
./gradlew :libs:common:test :apps:demo-api:test :apps:demo-worker:test --no-daemon --console=plain
```

소비자 회귀 2개를 추가한 뒤 `:apps:demo-api:test`를 다시 실행했다. 최종 모듈별 결과:

| 모듈 | 통과 | 실패 / 오류 / skip |
| --- | ---: | --- |
| common | 12 | 0 / 0 / 0 |
| demo-api | 9 | 0 / 0 / 0 |
| demo-worker | 4 | 0 / 0 / 0 |

회귀 테스트 8개를 추가했다. 관련 모듈 총 25개가 통과했으며 HTTP 배선 테스트는 실제 로컬 포트와 H2를 사용한다. Redis 경계 테스트는 모의 Redis 응답을 사용한다. MySQL/Redis/Kafka 컨테이너 통합 테스트는 로컬 WSL에서 Docker가 연결되지 않아 실행하지 않았다. 원격 CI 결과는 해당 커밋의 Checks에서 별도로 확인한다.

소유자 비교의 시간은 세션 ID 길이에 비례하며 추가 공간은 상수다. 처리량이나 전체 서비스 지연의 개선률은 측정하지 않았다. 정상 소유자, 다른 세션, 만료 상태와 비활성 상태를 기존 테스트와 함께 유지한다.
